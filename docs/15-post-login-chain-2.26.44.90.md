# Post-login chain of 2.26.44.90 — step by step

Everything the client sends and receives right after `<success>` on a fresh registration,
with the concrete parameters observed in the live capture
(`hooks/wa_agent_log_registration.txt`, Frida hooks on `X.1sR.A05/A06`).

Direction: **IN** = server → client, **OUT** = client → server.
`W<n>` is the global write sequence number of the capture (order of writes, not strict
network order — the client runs several threads in parallel).

## Step 0 — `<success>` (IN)

Server confirms the Noise handshake and the login payload.

- The `t` attribute (server time, seconds) is parsed and stored in the login session
  object (`X.1t8.A02`); the local time (`clock/1000`) is stored in `X.1t8.A01`.
- This is the trigger for everything below.

## Step 1 — push config (OUT, W1)

```xml
<iq to="s.whatsapp.net" xmlns="urn:xmpp:whatsapp:push" type="get" id="1">
  <config version="1"/>
</iq>
```

- Purpose: fetch the push configuration (which push provider/token the server expects).
- `id` is the per-session request counter, starts at `1`.
- `config version="1"` — client-side config schema version, constant.

## Step 2 — unified session (OUT, W13)

```xml
<ib>
  <unified_session id="127334115"/>
</ib>
```

- `id` — decimal session id generated by the client for this login (varies per session).
- `<ib>` carries no attributes; it is the "instant bullet" container for fire-and-forget
  nodes.

## Step 3 — media connection (OUT, W88)

```xml
<iq xmlns="w:m" type="set" to="s.whatsapp.net" id="01">
  <media_conn last_id="49829133"/>
</iq>
```

- `last_id` — the last media connection id known to the client (integer, from prefs).
- `id` becomes `01` (2-digit sequence after the first request).

## Step 4 — ACS v1: `sign_credential` (OUT, W98)

```xml
<iq xmlns="privatestats" type="get" to="s.whatsapp.net" id="05">
  <sign_credential version="1">
    <blinded_credential>32 bytes</blinded_credential>
  </sign_credential>
</iq>
```

- `blinded_credential` — 32 random bytes, blinded client credential (ACS v1); the server
  returns `t`, `signed_credential`, `acs_public_key` and a DLEQ proof
  (see `12-post-login/acs-privatestats.md`).
- `version="1"` — ACS v1 (v2 comes later in the session, see step 18).

## Step 5 — ToS version (OUT, W103)

```xml
<iq xmlns="tos" type="get" to="s.whatsapp.net" id="06">
  <request>
    <notice id="20210210"/>
  </request>
</iq>
```

- `notice id` — the ToS notice version the client currently knows (`20210210` observed).
- The server answers with the current ToS text/ids; if the version changed, the client
  shows the ToS screen.

## Step 6 — prekey upload (OUT, W118)

```xml
<iq id="2" xmlns="encrypt" type="set" to="s.whatsapp.net">
  <identity>32 bytes</identity>              <!-- identity public key -->
  <registration>4 bytes</registration>       <!-- registration id, e.g. 7493e9c5 -->
  <type>05</type>                            <!-- key type: 0x05 = Curve25519 -->
  <list>
    <key id="0bb469"><value>32 bytes</value></key>
    ...
  </list>
  <skey id="59d197">
    <value>32 bytes</value>                  <!-- signed prekey public -->
    <signature>64 bytes</signature>          <!-- XEdDSA signature over skey -->
  </skey>
</iq>
```

- Observed: 40+ one-time prekeys in `<list>`, each `id` is 3 random bytes, `value` 32 bytes.
- `registration` = the 4-byte registration id also sent as `e_regid` during registration.
- `skey.signature` is 64 bytes (XEdDSA), verified by the server against `<identity>`.
- This stanza is the first consumer of the Signal key material created at registration.

## Step 7 — keystore attestation (OUT, W4203)

```xml
<ib>
  <keystore_attestation>3420 bytes DER</keystore_attestation>
</ib>
```

- Single binary child, no attributes.
- Before it, the client computes the chain: `X.17x.A04` with a 32-byte `p2`
  (challenge random part), `mode=0`; the challenge is
  `uint64BE(seconds) ‖ 0x1F ‖ p2(32)`.
- Gate: AB 1934 + AB 1935; throttled by AB 2067 (`ka_stanza_sent_ts`).
- Position: immediately after `unified_session`, before the first `w:stats` batch.

## Step 8 — gpia / Play Integrity JWS (IN + OUT, W4287)

Server:

```xml
<ib><gpia><request nonce="..."/></gpia></ib>
```

Client:

```xml
<ib><gpia><jws>...</jws></gpia></ib>
```

- `nonce` — server-provided integrity nonce.
- `jws` — the Play Integrity token (JWS) bound to that nonce, produced by the app's
  integrity pipeline; length observed in the capture is in the `W4289` neighbourhood.
- The pair `gpia`/`safetynet` replaces the old SafetyNet flow; both are still present.

## Step 9 — num_acc / platform (OUT, W4235)

```xml
<ib>
  <num_acc>2</num_acc>
  <platform>gcm</platform>
</ib>
```

- `num_acc` — account counter/number as known to the client.
- `platform` — push platform (`gcm` = Google Cloud Messaging / FCM).

## Step 10 — integrity_payload (OUT, W4242)

```xml
<ib>
  <integrity_payload>1024 base64 chars</integrity_payload>
</ib>
```

- 768-byte blob: `base64_std( IV[16] ‖ AES-256-CBC(PKCS7(JSON)) )`, key =
  `SHA256(std_base64(authkey))`.
- The JSON contains `aid`, `_dh`, `_lh`, `_iln`, `_ln`, `_ge`, `_gp`, `_ga`, `_ip`,
  `_isb`, `_n`, `_icr`, `_is` (see `05-integrity/_lh.md`).
- Sent in response to the server `<safetynet><integrity nonce="...">` request.

## Step 11 — account bootstrap queries (OUT)

| `get_user_disclosures` | `t=1794915236` | fetch the user disclosure list |
| `w:b` → `lists` | list identifiers | business lists |

## Step 12 — presence (OUT, W4764)

```xml
<presence type="available"/>
```

- Announces the client as online; after this the server starts delivering messages.

## Step 13 — sync_results (OUT, W4963)

```xml
<sync_results eval_ts_sec="..."/>
```

- Result of the initial state synchronisation (`eval_ts_sec` — server evaluation timestamp).

## Step 14 — w:stats batches (OUT)

```xml
<iq xmlns="w:stats" type="set" to="s.whatsapp.net" id="02">
  <add t="1794914537">...</add>
  <add t="...">...</add>
</iq>
```

- `t` — event timestamp (seconds).
- Payloads are encrypted blobs of 830–1278 bytes (`WAM\x05\x00…` header), sent in batches.

## Step 15 — comms / promotions (OUT, W5104)

```
w:comms:chat  → query blocking_status
w:comms       → event { promotion_id, timestamp_sec }
              → logdata / impression / optoutlist
```

- New channel relative to 2.26.35.75: promotions and their telemetry
  (`promotion_id`, `timestamp_sec`, `logdata`, `impression`, `optoutlist`).

## Step 16 — ent:silent_nonce (OUT, W5360)

```xml
<ent:silent_nonce>16 bytes</ent:silent_nonce>
```

- 16-byte nonce for the silent "ent" verification tier.

## Step 17 — ACS v2 (OUT, W5152)

```xml
<iq xmlns="privatestats" type="get" to="s.whatsapp.net">
  <sign_credential version="2">
    <project_name>...</project_name>
    <config_id>...</config_id>
  </sign_credential>
</iq>
```

- ACS v2: adds `project_name` and `config_id`; the response carries `t`,
  `signed_credential`, `acs_public_key` and a DLEQ proof.
- In the capture v2 appears later than v1 (W5152 vs W98), consistent with the
  "second credential for a different project" semantics.

## Step 18 — w:mex (GraphQL-like) requests

```xml
<iq xmlns="w:mex" type="get" to="s.whatsapp.net" id="0a">
  <trace><flow_id>25863197129975892</flow_id></trace>
  <query query_id="25863197129975892">{...}</query>
</iq>
```

- `trace.flow_id` and `query.query_id` are equal decimal ids; the `<query>` body is a JSON
  document (`{"queryId":"...","variables":{...}}`).
- ~35 such requests in the first two minutes: feature flags, AB props, newsletters,
  blocking status, etc.

## Ordering summary

```
<success>
  → iq(push/config) → ib(unified_session) → iq(w:m media_conn)
  → iq(privatestats sign_credential v1) → iq(tos)
  → iq(encrypt: identity+registration+list+skey)
  → ib(keystore_attestation 3420B)
  → gpia/request ⇄ gpia/jws
  → ib(num_acc/platform)
  → ib(integrity_payload 768B)
  → get_user_disclosures, w:b lists, newsletter, my_addons
  → presence(available)
  → sync_results
  → w:stats batches
  → w:comms (chat/blocking_status, event promotion)
  → ent:silent_nonce
  → ACS v2 (sign_credential version=2)
  → w:mex queries (continuous)
```

Note: the order above is the order of writes in the capture; several nodes are emitted
from different threads and may interleave on the wire.
