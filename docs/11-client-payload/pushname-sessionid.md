# Fields 7 pushName and 9 sessionId

ClientPayload `X/C1HS.java`, build 2.26.35.75 (263507522). The two fields are set by
the case 6559 filler (`X.1J8`, sessionId — `X/C1US.java:20341-20345`) and the case
6561 filler (`X.1JV`, pushName — `X/C1US.java:20724-20732`).

## pushName (field 7, string)

Constant: `PUSH_NAME_FIELD_NUMBER = 7` (`X/C1HS.java:47`); the value default is
`Voip.REJECT_REASON_DECLINED` = `""` (`X/C1HS.java:93`).

The `X.1JV` filler code (`X/C1US.java:20724-20732`):

```java
String strAvj = ((C08X) this.A00.A00.get()).Avj();
C000800h.A06(strAvj);                       // null-check
if (strAvj.length() != 0) {
    c1hs3.bitField0_ |= 16;
    c1hs3.pushName_ = strAvj;
}
```

Properties:

- The source is `C08X.Avj()`: the public profile name (the "WhatsApp name") that the
  owner sets for themselves. `C08X` is the "Me" provider interface; the
  implementation stores the name in the account's user data.
- The field is set **only if the string is non-empty**: an empty name (the account
  was just created, the name has not been set yet) — the field is absent from the
  payload entirely, bit 16 of `bitField0_` is not set. Null is impossible — there is
  an explicit null-check (`A06`).
- The value is the same for all connection attempts until the user changes the name;
  it is also sent in `<iq xmlns='w:profile:picture'>`/usync during synchronization,
  so the server can cross-check the pushName from the payload against the profile.
- Do not confuse the name with `username` (field 1): `username` is the numeric JID,
  `pushName` is the text visible to counterparts.

In the first-login capture the account was created 6 seconds before the connect
(`creation='1788392926'`, socket accepted at `t='1788392932'`). By that moment the
profile name is usually already entered in the registration wizard — then the field
is sent populated; if the step was skipped, the field is simply absent. In the same
capture, right after `<success>` the client receives a `usync` with
`context='registration'` — the name is synchronized through the regular nodes as well.

## sessionId (field 9, int32)

Constant: `SESSION_ID_FIELD_NUMBER = 9` (`X/C1HS.java:48`).

The `X.1J8` filler code (`X/C1US.java:20341-20345`):

```java
int i7 = c1hm.A02;                 // XmppLoginContext.sessionId
c1hs5.bitField0_ |= 32;
c1hs5.sessionId_ = i7;
```

Properties:

- Written **always**, unconditionally — one of the filler's four unconditional int
  writes (sessionId, shortConnect, lc, connectReason).
- The source is `C1HM.A02`, the `sessionId` field of the `XmppLoginContext` context
  (`X/C1HM.java:82-94`, toString "sessionId="). The context is assembled in `C0SW.A0v`
  (`X/C0SW.java:1634`, the `c1fb.A07(...)` call) for every login attempt; the
  identifier distinguishes connection attempts from each other in client logs and
  metrics.
- It is an int32, generated by the client, not issued by the server. In the log
  `ConnectionThread/connect: SEND <handshake_payload ... session_id=...> ...`
  (`X/C0SW.java:1643-1655`) the value is printed in the clear before encryption —
  the simplest way to link a specific ClientPayload to a specific connection in the log.
- Next to it, in `C1FP` (connectionMetadata, `X/C1FP.java`) there is its own `A07`
  with the same `sessionId` name in toString — that is the socket session identifier,
  used for `connectionSequenceInfo` (field 43), not for field 9.

## Trace in the capture after `<success>`

Right after the payload is accepted, the client sends twice
(02:48:52.461 and .497):

```xml
<ib><unified_session id='258531227'/></ib>
```

`unified_session` is a server-client identifier of the unified session; it is not
equal to the payload sessionId (that one is generated on the device and never appears
in the clear XML), but it appears in the same second: this node is a convenient way
to locate the moment that this connection's payload corresponds to.
