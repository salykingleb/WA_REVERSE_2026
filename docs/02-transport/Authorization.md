# Authorization — header with the keystore attestation certificate chain

## Place in the flow

`Authorization` — an HTTP header of the POST requests `/v2/code` and `/v2/register`,
carrying the DER concatenation of the Android Key Attestation certificate chain:
**root → TEE-CA → device-TEE → leaf**. The header is paired with the `H` signature: the leaf
certificate of the chain contains the public key with which the server verifies `H`, and the
attestation extension KeyDescription inside the leaf binds the key to the device (TEE), the
WhatsApp APK and the challenge (= the client's authkey). Assembly — `RetryingHttpClient.A00`, tag
`RegistrationBodyBuilder/getAttestationPayload` (dexdump classes9.dump, offsets
0x02c3–0x02fa, `const-string "Authorization"`).

## Wire format (type, encoding, length, LIVE example from the capture)

```
Authorization: <base64.Std(DER(root) || DER(TEE-CA) || DER(device-TEE) || DER(leaf))>
```

- Encoding: `Base64.encodeToString(bytes, 2)` = standard alphabet with `=` (flag 2 =
  NO_WRAP; without line breaks) — NOT url-safe, unlike ENC/H.
- Order: Android Keystore returns the chain [leaf, …, root]; the app writes it
  in the REVERSE order — from root to leaf (see the code below). Result: the last base64 block is the leaf.
- Length: 4 DER certificates (~600–900 B each) → ~2.5–3.5 KB binary → ~3.5–4.7 KB base64.
- The header is put into the header map only when attestation is enabled; its position
  on the wire — after `WaMsysRequest` (native order) / at the end of the map (Kotlin path).
- The live header value is absent in the text dump (the dump contains only the URL);
  the structure was reconstructed from the dexdump code and live keystore chains from captures
  (see the comparison below).

## How it is built in the app (Java/Kotlin class file:line, code fragments)

`X/C13D.A03` (C13D.java:615–641), verbatim:

```java
public static byte[] A03(C13D c13d, Integer num, byte[] bArr) {
    if (!c13d.A06()) return null;                       // AB-флаг 1934
    c13d.A02(num, bArr);                                // гарантия свежей пары (challenge=authkey)
    KeyStore keyStore = KeyStore.getInstance("AndroidKeyStore");
    keyStore.load(null);
    Certificate[] chain = keyStore.getCertificateChain(
            num == C02S.A01 ? c13d.A01() : c13d.A00()); // static alias для регистрации
    ByteArrayOutputStream out = new ByteArrayOutputStream();
    if (chain != null) {
        for (int i = chain.length - 1; i >= 0; i--) {   // РЕВЕРС: [leaf..root] → [root..leaf]
            out.write(chain[i].getEncoded());           // DER каждого сертификата подряд
        }
    }
    return out.toByteArray();
}
```

Then in RetryingHttpClient.A00: `X/B0Y.A1E(bytes)` (B0Y.java:45) =
`Base64.encodeToString(bytes, 2)` → the value of the `Authorization` header.

The call from the registration flow: `C13D.A03(c13d, C02S.A01 /*static alias*/, authkeyPub)` —
the same challenge/authkey that goes into the pair generation for H (see H.md).

**Key alias**: `my_personal_mini_pony_static` (+ an optional `_`-UUID suffix,
pref `ka_key_store_static_alias_suffix`) — C13D.java:47–64.

## Native implementation (if involved)

The certificate contents are generated by the device's keymaster/TEE (or by the remote
Google provisioning service — see the live chains below): the Java layer only sets
`setAttestationChallenge(challenge)` on the `KeyPairGenerator` (C13D.A02:193), while the DER
of the certificates and the KeyDescription extension are produced by the TEE. There are no `_WCAPI*` functions here;
in the native wamsys path the header is passed already assembled (provider C13D id 2874,
the keystore id 6015 — `X/AbstractC39157HWs`).

## Conditions for choosing values (variants, ranges, when absent)

- **Absent** when `C13D.A06()` = false (AB flag 1934 off) or the chain could not be
  obtained (log `blacknoise/exception on certificate chain retrieval`,
  event `attestation-nocertchain`).
- Registration always uses the **static alias** (`C02S.A01` → `A01()`).
- The Business build attests with its own packageName/versionCode (`com.whatsapp.w4b` /
  263607214); consumer — `com.whatsapp` / 263507522.
- With `AnonymousClass075.A06()` the spec gets
  `setDevicePropertiesAttestationIncluded(true)` added, with a fallback to false on
  ProviderException (C13D.A02:195–209).
- Pair freshness — the AB 4878 s interval over `ka_static_refresh_ts` (see H.md).

## Cryptography and encoding

**The challenge in KeyDescription** (pair generation, C13D.A02:186–193):

```
challenge = 00000000 || uint32_BE(unixSeconds) || 0x1F || authkey_raw(32B)   // 45 байт
```

(putLong BE 8 bytes → with unixtime < 2^32 the high 4 bytes are zero; then the literal
byte 31 = 0x1F; then the client's public authkey — `X/AnonymousClass139.A0I()`.)

**KeyDescription** — the leaf certificate extension OID 1.3.6.1.4.1.11129.2.1.17,
filled in by the device keymaster (live capture profile of 2.26.35.75, TEE):

| Field | Value |
|---|---|
| attestationVersion | 3 |
| attestationSecurityLevel | TEE (1) |
| keymasterVersion | 4 |
| keymasterSecurityLevel | TEE (1) |
| attestationChallenge | 45B: `00000000 ‖ uint32BE(unix) ‖ 0x1F ‖ authkey` |
| uniqueId | empty |
| softwareEnforced | [701] creationTimeMS, [709] applicationID |
| teeEnforced | [1] purpose = {2} (KM_PURPOSE_SIGN), [2] algorithm = 3 (EC), [3] keySize = 256, [5] digests = {4 (SHA-2-256), 6 (SHA-2-512)}, [10] ecCurve = 1 (P-256), [503] attestationApplicationId/`NULL` variant per profile, [702] origin = 0 (GENERATED), [704] rootOfTrust, [705] osVersion, [706] osPatchLevel, [718] vendorPatchLevel, [719] bootPatchLevel |
| rootOfTrust | verifiedBootKey, verified = true, verifiedBootState = 0 (Verified), verifiedBootHash |
| osVersion | android version × 10000 (e.g. Android 13 → 130000) |
| packageName | com.whatsapp |
| apkVersionCode | 263507522 |
| apkDigest | `OYfQQ9EK769ahxCzZxQY/lfg4ZtlPJ34JVj+tf/OXUQ=` (base64.Std SHA-256 of the APK signature) |

The purpose tag in KeyDescription = {2} (KM_PURPOSE_SIGN) — this is the keymaster equivalent of
purpose 4 (PURPOSE_SIGN) from `KeyGenParameterSpec.Builder(alias, 4)` (C13D.java:177).

**Leaf certificate**: subject CN = "Android Keystore Key"; signed by the device key
(device-TEE / keybox). Verifying the chain up to the trusted root and the KeyDescription,
the server makes sure: the key is in a hardware TEE, was created for signing, belongs to the WhatsApp
APK with the given digest/versionCode, the challenge matches the client authkey from the ENC query.

**Comparison with live keystore chains from captures**:

- The September 2026 capture (2.26.35.75, SM-A325F, Samsung TEE): the classic
  **Samsung TEE chain** — root → Samsung TEE-CA → device-TEE (keybox) → leaf
  `CN=Android Keystore Key`. It is exactly this profile that corresponds to the four-link
  structure root→TEE-CA→device-TEE→leaf.
- The login capture of 28.09.2026 (2.26.37.73, the same phone): a **Google remote
  provisioning** chain — Key Attestation CA → Droid CA2 → Droid CA3 (TEE `ccad9877…`) →
  leaf `CN=Android Keystore Key`. That is, on one and the same device the chain profile depends
  on the keymaster key issuance method (local keybox vs remote provisioning);
  the "root→…→leaf" order and the basic KeyDescription structure are unchanged.

## Examples

The header scheme (4 DER blocks, NO separators — just a byte concatenation):

```
Authorization: MIICizCCAjKgAwIBAgIB…<root ~850B DER>…MIICezCCAjKgAwIBAgIB…<TEE-CA>…MIICcTCCAdigAwIBAgIB…<device-TEE>…MIIB…<leaf: CN=Android Keystore Key, содержит KeyDescription с challenge 00000000‖BE32(0x68F2…)‖1F‖<authkey 32B>>…
```

Live context for verification: the authkey of the same session =
`rsgyL8y0zyOXIJT4KofOJGJaxrlKUp6TuBsPvGzZAzs` (43 chars of b64url = 32B) — these same 32
bytes must stand as the tail of the challenge inside the KeyDescription of the leaf certificate;
the H signature is verified with the key of exactly this leaf.
